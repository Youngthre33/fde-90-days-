# Day 87：用日志追踪一次工单请求

## 本节解决什么问题

用户通过浏览器或 Swagger 操作工单（一条需要处理的问题记录）时，我们需要知道：是哪次请求、查询了哪条记录、处理用了多久，以及出错时停在了哪里。
本节给工单应用增加终端日志、请求编号和耗时记录，让一次请求的相关记录可以串起来。
“接口”是供其他程序通过 HTTP 请求使用的功能，例如发送 `GET /tickets/101` 来查询记录。FastAPI 框架就是安装在 Python 环境中的一套现成代码，负责按我们登记的规则找到函数、检查输入并组织回复。

## logging：把程序经过的事情记下来

`logger = logging.getLogger(__name__)` 获取当前模块使用的日志记录器，可以把它理解成“负责记事的工具”。
通过模块名导入应用时，这个记录器的名字是 `day87.main`。
`run.py` 中的 `logging.basicConfig(...)` 设置基础输出级别和格式：

```text
时间|级别|记录器名字|具体消息
```

例如：

```text
14:20:05|INFO|day87.main|请求开始，request_id=示例编号, method=GET, url=/tickets/101
```

- `INFO`：普通过程记录，例如请求开始、请求结束、查询成功。
- `WARNING`：需要留意的情况，例如要查询的工单不存在。
- `ERROR`：发生了需要排查的异常；本节的 `logger.exception(...)` 使用这个级别。
- `DEBUG`：比 `INFO` 更细的级别；本节自定义日志没有调用 `logger.debug(...)`。

配置级别相当于显示门槛：`debug` 或 `info` 能看到本节的全部自定义过程日志。
若配置为 `warning`，`INFO` 会被过滤，因此后面的日志条数核对要使用 `debug` 或 `info`。
日志消息中的 `%s` 是留给后续参数的位置，`%.2f` 表示小数保留两位。

当前基础日志输出到终端的标准错误流（`stderr`），没有写入日志文件。
“标准错误流”是输出通道的名字，不代表其中每一行都是错误；普通 `INFO` 也可以走这个通道。
Uvicorn 自己的启动、访问和错误记录可能同时出现，核对条数时只数本节写的自定义日志。

## 中间件：在接口处理前后各做一次事

`@app.middleware("http")` 注册 HTTP 中间件，可以理解成请求进入接口、响应离开接口时经过的一道公共处理步骤。
本节正常流程如下：

```text
收到请求 → 生成请求编号、记开始时间、写开始日志
        → await call_next(request) → 接口处理并生成响应对象
        → 计算耗时、写结束日志、给响应加请求编号 → 返回响应
```

`call_next` 是框架传给中间件的函数参数，负责让请求继续交给后面的处理流程。
`await call_next(request)` 等待这次调用得到响应对象；当前中间件先停在这一行，拿到回复后再往下执行，服务器在适当的等待期间仍可处理其他请求。

`request` 是请求对象，里面有客户端发来的路径、方法等信息。
`response` 是响应对象，里面有准备回复的状态码、响应头和内容。
二者分别代表“收到什么”和“准备回复什么”，不是同一个对象。

## 请求编号、工单编号与耗时

| 名称 | 通俗理解 | 本节的用途 |
| --- | --- | --- |
| `request_id` | 这一次访问的编号 | 用 `uuid4().hex` 生成，把同一次请求的多条日志串起来 |
| `ticket_id` | 要处理的工单编号 | 例如工单 101，可以被很多次不同的请求查询 |
| `request.state.request_id` | 挂在本次请求上的临时便签 | 中间件先写入，查询工单的接口随后读取 |
| `X-Request-ID` | 回复中附带的一项信息 | 客户端从响应头取得编号，方便与终端日志核对 |

重复查询工单 101，`ticket_id` 可以不变，但每次请求都会生成新的 `request_id`。
`request.state` 只用于这次请求期间共享信息，不是所有请求共用的全局存储，也不会自动保存到数据库。
响应头与 JSON 响应内容是两部分；增加 `X-Request-ID` 不会给工单 JSON 自动增加字段。

`perf_counter()` 是适合测量耗时的计时器，不是用于显示日期的时钟。
两次读数相减得到秒，再乘以 1000 得到毫秒：

```python
duration_ms = (perf_counter() - start_time) * 1000
```

正常情况下，这段耗时测到中间件取得响应对象为止；它不代表客户端完整收到数据的网络往返时间。
异常情况下，测到异常被中间件捕获为止。

## 异常日志与重新抛出

`try` 包住继续处理请求的调用；如果调用中有未被处理的异常，`except Exception` 接住它。
`logger.exception(...)` 写出 `ERROR` 消息，并附上 traceback（错误追踪信息，也就是出错时经过的代码位置）。
它在这里放在 `except` 中调用，才能记录当前捕获到的异常。

随后单独一行的 `raise` 叫“裸 raise”，意思是把当前捕获的原异常重新抛出去。
因此代码记录完错误后，仍由框架处理这个失败请求，客户端得到默认的 500 响应。
异常分支不会继续执行后面的正常结束日志和加响应头语句。
所以本方案的这类 500 **没有设置 `X-Request-ID` 响应头**，应在终端的异常记录中找请求编号。

工单不存在时的 `HTTPException(404)`，以及参数不合法时的 422，通常已由框架转换成响应对象。
它们会经过本节的“请求结束”日志，不会进入这里记录未处理异常的 `except` 分支。
客户端返回 500 和终端保存详细异常是两件事：Swagger 展示响应，终端展示错误追踪信息。

## 一次完成的核对

保持服务器运行，日志级别使用 `debug` 或 `info`，在 Swagger 中依次发起下面的 GET 请求。
下面以初始数据中仍存在工单 101、尚无工单 999 为前提；若此前修改了内存数据，先重启恢复初始数据。

| 请求 | 预期状态 | 本节自定义日志 | 响应头核对 |
| --- | --- | --- | --- |
| `/tickets/101` | 200 | 4 条：请求开始、查询开始、查询成功、请求结束 | `X-Request-ID` 与这 4 条日志中的编号一致 |
| `/tickets/999` | 404 | 4 条：请求开始、查询开始、查询失败、请求结束 | `X-Request-ID` 与这 4 条日志中的编号一致 |
| `/tickets/0` | 422 | 2 条：请求开始、请求结束 | `X-Request-ID` 与这 2 条日志中的编号一致 |
| `/health` | 200 | 2 条：请求开始、请求结束 | 返回 `{"status":"ok"}`，响应头编号与日志一致 |

`/tickets/0` 没有查询业务日志，是因为 `Path(ge=1)` 的参数校验先拦住了它，查询函数体没有执行。
每次核对只比较同一次请求的编号，不要把不同请求的编号混在一起。
打开 `/docs` 时产生的页面、接口定义等请求也可能有日志，不计入上表的单次请求条数。

本次学习已经通过临时故意除零看过 Swagger 的 500 和终端的异常追踪信息。
临时 `/debug/error` 路由已从当前源码删除，不属于正式工单接口，也不需要为了日常核对重新加入。
练习此类故意出错的入口后必须删除，并重启加载新代码，避免让调试入口留在应用中。

## 当前边界

工单仍保存在进程内存中，重启会恢复初始数据；本节没有新增数据库或登录认证。
日志只输出到终端，没有日志文件、轮转或集中存储；请求编号用于查找相关记录，不代表访问权限。
本节完成的是“能看到一次请求经过了什么、用了多久、失败在哪”，为后续排查问题提供依据。
