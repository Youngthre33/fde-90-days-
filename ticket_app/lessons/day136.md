## 第一段：创建账号、建立连接、观察授权前的行为

使用原有postgres管理员连接，在同一PostgreSQL服务的Login/Group Roles上右键Create→Login/Group Role。账号是服务所属集群的登录角色，多个数据库共享这份身份；账号名称不同于数据库名称，也不同于pgAdmin连接的显示名称。

- General→Name：ticket_app_user。
- Definition→Password：学习者自己设置并本地保存，不写入讲义或Git，不要求发给教师。
- Privileges→Can login：Yes；Superuser、Create roles、Create databases均No。其他管理选项保留默认，Membership不加入其他角色。
- Save；已有同名账号或错误时报告，不默认重建/修改已有角色。

之后在pgAdmin的Servers节点Register→Server，新增显示名称“Day136 应用账号”。Connection填写127.0.0.1、5432、Maintenance database=ticket_app_test、Username=ticket_app_user，以及刚设置的密码；Role字段留空。这份配置仍连接同一个本机PostgreSQL服务，只使用新的登录身份。

从新连接里的ticket_app_test打开Query Tool，先执行：

```sql
SELECT current_user AS db_user, current_database() AS db_name;
```

current_user是当前执行SQL的身份，此处没有括号；current_database()返回连接库名；AS起结果列名。预期账号ticket_app_user、库名ticket_app_test。连接失败时先反馈错误，不继续假设身份已切换。

再单独执行：

```sql

FROM public.tickets
LIMIT 1;
```

三行分别指定字段、表、最多返回一张工单。目前尚未向新账号授予练习表的操作权限，预期permission denied for table tickets。该错误说明已提交表查询但权限不足，不能当作数据库不存在或连接失败。实际若返回记录，先反馈，核对是否已有授权或用错账号；不凭预期虚记拒绝。

## 第二段：管理员授予对象权限，新账号重新读取

从原postgres管理员连接的ticket_app_test打开Query Tool，确认窗口目标为该库及管理员账号，再执行：

```sql
GRANT USAGE ON SCHEMA public TO ticket_app_user;

GRANT SELECT, INSERT, UPDATE, DELETE
ON TABLE public.tickets
TO ticket_app_user;

GRANT SELECT ON TABLE public.ticket_events TO ticket_app_user;
```

GRANT授予权限，ON说明作用对象，TO指定接收账号。第一句明确允许使用当前库的public schema中的对象，此项不单独授予表操作；第二句给tickets已有表增删改查权限；第三句只给当前应用读取处理记录所需的SELECT，其他操作按后续真实需求再授权。对象授权生效于当前连接库，不自动授予其他数据库同名表，也不包含今后新建表。普通账号能连接已有默认权限的其他数据库，不代表能操作那些表。

pgAdmin默认自动提交时授权执行成功即生效；若关闭了Auto commit，管理员须提交后再从另一连接核对。授权语句通常在Messages显示GRANT，不返回工单数据行。实际成功尚待用户报告。

回到“Day136 应用账号”下连接ticket_app_test的Query Tool，分别执行：

第一条预期不再出现tickets权限拒绝，第二条检查处理记录读取；表没有记录时0行也可说明本次读取被允许，不凭0行推断对象缺失。真实结果尚待反馈。只读成功不能证明新增/修改/删除已实际验证，写入和管理权限检查在下一段给出。账号身份仍为ticket_app_user；业务配置和运行中的Python账号未调整。

## 概念补讲与疑问

### 学习者追问：schema的USAGE与多条授权

学习者问“使用权限具体是什么，能否一条命令写完，还是为了看清分开”。补讲以 `SELECT ... FROM public.tickets` 为例：schema USAGE允许SQL引用/查找该schema中的对象；是否可读取或修改表还要满足表自身的SELECT等权限，不等同于查看数据或获得schema内所有表权限，也不是建表的CREATE。能在pgAdmin看到名称不证明有数据读取权限。

同一GRANT授予某表多种权限可以用逗号合并，换行仅排版，末尾分号才结束当前语句。schema的USAGE与表的SELECT/INSERT/UPDATE/DELETE在普通GRANT语法中按不同对象类型分别写。两张表若授予相同权限也可列在同一ON TABLE后；本课tickets四种权限、ticket_events仅读取，所以分开表达。三条SQL可一次选中执行，仍是三条语句，不是一个万能GRANT。补讲不视为用户已理解或授权已运行，仍待实际反馈。

### 学习者追问：数据库、schema、public、表与对象

学习者仍不理解USAGE，指出不清楚Schemas→public→Tables的层级，并把ticket_app_test称为表，问“对象”是什么。暂停推进授权后的验证，先补基础：ticket_app_test是数据库；数据库中有schema，public是其中一个schema的名字；tickets和ticket_events是其中两张表。Schemas与Tables是pgAdmin界面的列表分组，实际命名层级是数据库→schema→表，不能把所有界面节点当成独立存储层。

这里“数据库对象”是数据库中被命名、引用和管理的具体东西的统称，本例就用两张表说明，不引入更多陌生对象类别。public.tickets表示public这个schema里的tickets表。以SELECT title FROM public.tickets WHERE id=5为例：FROM指定表，WHERE找该表中的行。schema USAGE允许引用schema内对象，表SELECT允许读取数据；“找对象”不是筛选工单行，也不是通过左侧展开节点改变权限。补讲后仍待学习者理解反馈，不虚记已掌握；授权与授权后读取仍无实际执行报告。

学习者随后复述Schemas菜单是集合、public是其中一个schema、区域内有表、tickets是对象，层级理解正确。补清单数schema、复数schemas；表逻辑上属于public，Tables是界面显示清单，不是实际保存数据的菜单。该答案确认本次层级与对象基础理解，不替代GRANT与授权后操作结果。接续把三句授权、两表读取、专用工单新增集中给出，待实际编号和操作反馈。

### 学习者追问：只有USAGE不能读写，引用实际有什么用

学习者正确回答仅USAGE不能SELECT后继续追问实际用途。不能只重述“引用权限”而不解释作用：schema的USAGE是普通账号直接访问其中对象时所需的一项权限，通常与具体表的SELECT/INSERT/UPDATE/DELETE配合，不单独产生查询结果。用SELECT title FROM public.tickets说明FROM public.tickets指定目标表、SELECT title请求读取标题；两部分对应不同层的权限要求。只给USAGE而没有相应表权限，仍不能直接读写这张表；反过来，只有表SELECT而没有schema使用权限也不足以完成这条直接查询。这样可以允许账号使用同一schema，但只给tickets增删改查、ticket_events读取，不扩大到区域内所有表/所有操作。讲解没有执行任何权限变动，不要求撤销授权实验。学习者随后明确回复“我懂了”，按理解自述记用途已补清，结合此前理解题正确答案，不追加同类题；应用写入也已报告正确，Git仍待反馈。
