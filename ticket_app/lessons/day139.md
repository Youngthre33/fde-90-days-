## 本课用途

Day138已观察文件服务启动/停止、进程和日志；现在沿用该服务，学会区分请求没有连到目标服务与服务收到请求后找不到资源。现实中浏览器打不开时，可以先定位应检查连接目标还是资源路径，不随意同时改端口、代码和数据库。下一课再进入容器运行环境；本课没有新业务代码。

## 先看实际网址

```text
http://127.0.0.1:5501/constants.js
```

| 部分 | 在本次操作中的含义 |
| --- | --- |
| http | 浏览器使用HTTP发送请求、接收响应 |
| 127.0.0.1 | 本机回环地址；本次Windows浏览器经WSL本机转发访问Ubuntu服务 |
| 5501 | 本次文件服务接收请求的端口 |
| /constants.js | 交给该服务处理的资源路径；本例从指定web目录寻找这个文件 |

路径不普遍等于磁盘文件：本例http.server按目录提供文件，而后续8001上的/tickets是工单接口，由main.py等业务代码处理。地址和端口选定目标之后，资源路径由收到请求的服务解释；同一台电脑的不同端口不会自动找到同一个程序。

## 操作位置与服务准备

继续使用同一个Ubuntu的A终端，Windows浏览器负责发请求。本轮无需B终端、无需数据库。如果A仍显示文件服务的运行日志，保持运行，不重复启动。只有A已退出且出现shell提示符时，才在项目目录执行原命令：

```bash
python3 -m http.server 5501 --bind 127.0.0.1 --directory ticket_app/web
```

需要重新定位目录时先单独执行cd /mnt/c/Users/Administrator/Documents/GitHub/fde-90-days-。命令角色沿用Day138，不新建脚本、不改CORS或API地址。已有端口占用时报原输出适配，不停止无关进程。

## 一次完成三个请求对照

分别在Windows浏览器地址栏打开下列URL，每次观察页面结果，再看A中这次请求对应的路径和状态。网页额外的favicon.ico请求与目标路径分开看，不将其404误认为constants.js失败。

1. http://127.0.0.1:5501/constants.js：预期取得文件，新的正常文件请求日志是GET /constants.js及200；若缓存核对出现304，可用Ctrl+F5再请求。实际结果以反馈为准。
2. http://127.0.0.1:5502/constants.js：仅将端口改为5502。若该端口没有HTTP服务，浏览器通常无法连接，也不会直接向5501的A服务发出此请求。未独立检查5502占用，不预认该端口必为空；若能打开页面，用户报告显示内容，说明可能有另一服务，按事实调整对照，不停止它。
3. http://127.0.0.1:5501/day139_missing_file.txt：仍使用正确端口，但请求web目录中不存在的文件。预期服务返回404 File not found，A出现该路径的GET和404；如果实际取得内容，反馈结果再核对文件，不把预期当事实。

第一项说明本次取得文件成功。第二项在无服务时失败在连接目标阶段，没有得到这个文件服务的HTTP响应。第三项收到HTTP 404，表示服务作出了响应但没有找到该资源；在本课先检查文件名、URL路径及提供的目录。404不证明工单数据库或全部其他服务正常，也不表示整台服务器一定停止。

## 两道理解题，实操后集中回答

1. 5501上的constants.js可以取得，改成5502却无法连接。能据此认定constants.js被删除了吗？优先核对什么？
2. 请求5501上的不存在文件，收到404且A记录了对应路径。这个请求是否到达了文件服务？首先核对请求路径/文件名，还是先重启服务？说明依据。
