# Day134：备份一个数据库并找到备份文件

## 本课小目标

在 pgAdmin 中备份整个 `ticket_app_test` 数据库，把数据库对象的定义和已保存的数据导出为一个备份文件。记录备份来源、实际文件路径、任务结果和文件大小。Day135 再把文件恢复到一个单独的新数据库并查询核对；本课不把文件生成算作恢复验证。

## 操作位置与步骤

先在测试库 Query Tool 重新核对数据库名与 Day133 的专用记录：

```sql
SELECT current_database() AS db_name, id, title, status, version
FROM public.tickets
WHERE id = 5;
```

必须确认 `db_name = ticket_app_test`，并记下当前真实标题与版本，作为后续恢复核对的依据。上一课报告的是版本 3，不沿用旧结果当备份时的实时值。

计划在 Windows 文档目录新建 `FDE-Backups` 文件夹，位于 Git 仓库之外。计划备份文件路径：

```text
C:\Users\Administrator\Documents\FDE-Backups\ticket_app_test_day134_20261001.backup
```

在 pgAdmin 左侧对数据库名 `ticket_app_test` 右键选择 Backup，而非对单张表操作。在 General 中将 Filename 设为上述完整路径，Format 选 Custom，其余设置先保持默认。Custom 是归档备份格式，之后通过恢复工具读取；`.backup` 是本课使用的文件名后缀，真正的格式由 Format 选项决定。

学习者回复“设置好 继续”，报告 General 的 Filename 与 Custom 格式已准备；未提供窗口截图、实际路径或来源查询中的版本值，教师未操作界面或数据库。

## 备份内容设置与执行流程

在 Data Options 中，Sections 的 Pre-data、Data、Post-data 均设为 Yes，以包含表和列等定义、实际数据和序列值、索引和部分约束。Type of objects 的 Only data、Only schemas 均为 No，避免限制为仅数据或仅结构。其他选项保持默认，不在 Objects 中限定只选一张表。

随后点 Backup。pgAdmin 在后台调用 `pg_dump` 连接所选的 `ticket_app_test`，读取对象定义与已保存数据，将归档写到 Filename 指定的位置。该导出不新增、修改或删除原工单；之后数据库发生的新修改不会自动写入已经生成的备份文件。

执行后查看 Processes 的本次 Backup 任务：Running 表示进行中，Finished 表示完成，Failed 表示失败，More details 可看日志。再在文件资源管理器确认目标文件存在且大小大于 0。要同时查看任务结果和文件，不能只凭一个文件名判断备份完整，也不把这两项当恢复验证。

## 关键理解题与实际讲评

1. 假设备份中 5 号工单为版本 3，备份后原库修改并提交为版本 4。学习者回答“不会，新的到的还是3，因为版本4之后没有进行备份”。判断和理由正确：已有文件不会随原库更新；用这份备份恢复，新库应得到备份中保存的版本 3。题中版本 3/4 是假设情境，不作为真实备份内容的独立证据。
2. 仅凭备份任务成功、文件存在且非零，能否认定恢复验证已完成？学习者回答“不能，应该查阅数据SELECT，核对内容结构，才能保证恢复成功了”。核心判断正确：还需实际恢复到新库，查询核对工单数据，并核对相应结构。补充操作区别：SELECT 查询记录；列类型、默认值、约束等结构可在 pgAdmin 的表定义中核对。下一课将实际操作，不能把本题答对记为恢复已完成。
