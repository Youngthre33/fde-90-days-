## 第1段：一次网页修改怎样保存到数据库

说明用的假设例子：20号工单标题从“打印机离线”改为“打印机无法连接网络”。编号只用于讲解，不指示操作真实20号工单。先阅读已有代码，不要求重新建立一套应用。

1. 用户在网页输入框打字：输入框的值变化，尚未发出保存请求。
2. web/main.js的handleSaveAction取得id和输入框值，fetch发PATCH /tickets/20，请求体包含新title。
3. main.py的TicketUpdate校验请求，update_ticket将已提供、非None的字段整理成update_data。
4. ticket_service.py当前的update_ticket_by_id把ticket_id和update_data交给repository；这条函数当前是转发，不凭文件名虚构额外校验。
5. ticket_repository.py用get_connection建立Psycopg PostgreSQL连接，使用已配置的ticket_app_user与日常ticket_app。下面标题分支位于with get_connection() as connection里面：

```python
if "title" in update_data:
    connection.execute(
        "UPDATE tickets SET title = %s WHERE id = %s",
        (update_data["title"], ticket_id),
    )
```

逐行含义：if先判断本次有没有标题字段；connection.execute把SQL和参数交给数据库；UPDATE选表、SET给title新值、WHERE以id限定行；两个%s分别对应新标题与工单编号；最后括号结束调用。SQL是数据库指令，参数值由Python取得后交给Psycopg处理。

6. 现有repository继续SELECT同一id并fetchone取得修改后的数据。正常退出这个Psycopg连接的with时提交当前事务并关闭连接；异常退出时回滚未提交事务并关闭。这是当前连接对象的行为，不能推广为所有with都会提交和关闭。
7. 成功提交后，row_to_ticket把查询行整理为Python字典；返回经过service、main，FastAPI生成HTTP JSON响应。
8. web/main.js的response.json读取响应，replaceTicket替换浏览器内存中的对应工单，setTickets保存新列表，render绘制页面并显示成功提示。

PostgreSQL负责持久保存日常数据库的数据文件；当前repository使用psycopg，不在ticket_app/tickets.db里保存这次修改。输入框、浏览器工单列表、Python查询结果、PostgreSQL中的记录应分清。

学习者看完流程表后要求“用代码走一遍，哪些代码起作用，比如main里的什么代码”。本轮不推进到下一主题、不催情境题，按以下源码顺序补讲，保留例子id=20、新标题“打印机无法连接网络”、原status=open；只对照代码，不操作真实20号。代码摘录允许调整换行、截取关键分支，但不修改业务文件。

5. update_ticket中的model_dump(exclude_unset=True,exclude_none=True)把本次实际提供的非None字段转成字典。本次update_data={"title":"打印机无法连接网络"}，没有status键，不把未填写的状态覆盖掉。函数调用update_ticket_by_id(ticket_id,update_data)时，main.py顶部导入指向service函数；调用未完成前，main在等待返回值。

7. repository的get_connection使用settings的host/port/dbname/user/password调用psycopg.connect并返回真实连接；配置来自此前设置，本轮不读取.env或打印密码。with get_connection() as connection用此连接执行title分支UPDATE，参数顺序为新标题、20；status未提供所以跳过status分支。随后SELECT同一id，fetchone得到假设元组(20,"打印机无法连接网络","open")。
8. return row_to_ticket(row)的缩进位于with外。先正常退出with，Psycopg提交当前事务并关闭本次连接，再执行该返回表达式；不是row_to_ticket、SELECT或return关键字本身承担提交。row_to_ticket按row[0]/[1]/[2]整理id/title/status字典；无行时返回None。
9. 字典依次返回repository→service→main的updated_ticket。main的if updated_ticket is None只处理找不到工单的404；本例有字典，走return updated_ticket。FastAPI按response_model处理并发送JSON响应。main的return先把结果交给框架，再经HTTP回到浏览器，不是直接调用浏览器JS函数。
10. main.js中fetch返回response，检查response.ok；response.json()读取并解析JSON为updatedTicket。replaceTicket在ticket.js遍历旧tickets数组，同id换成服务器对象，其他工单原样保留，得到newTickets。data.js的setTickets赋值tickets=newTickets，只更新浏览器内存。
11. editingId=null退出编辑显示；render(newTickets,editingId)调用renderTicketCount及renderTicketList。render.js非编辑分支的titleText.textContent用`${ticket.title} - ${statusText}`设置实际页面文字。actionMessage.textContent显示成功提示；finally恢复保存按钮，catch处理失败提示。

### console.error补讲与第一部分提交安排

学习者追问截图中的console.error，要求解释后提交。console是浏览器提供的控制台对象，console.error是按错误级别输出的方法；catch(error)中的error是接住本次错误的变量，这两个同名词不是同一对象。括号中依次传入固定日志标签、error.name（错误名称/类型）、error.message（说明文字），逗号分开参数，最后);结束调用。输出位置是运行网页的浏览器开发者工具Console，不是Python终端或页面提示区域。

为沿用准确描述保存状态的原则，日志固定标签也从“修改工单失败:”改为“标题保存流程出现异常:”。现在代码是：

```javascript
console.error(
    "标题保存流程出现异常:",
    error.name,
    error.message
);
```

例如后端返回422时，前面的if (!response.ok)主动throw new Error构造消息“修改工单失败,HTTP状态码:422”；catch变量接到它，name为Error，message为上述具体文字，console.error按顺序显示。此例仅解释，非现场出现错误，不自动认定数据库未保存。console.error本身只输出，不发送请求、不回滚、不再抛错。页面textContent给使用者提示，控制台日志给排查者提供详情。
