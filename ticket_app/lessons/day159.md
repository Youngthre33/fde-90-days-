### 同一份数据逐行跟踪

1. advice_cache = {}：Python 创建空字典，由 advice_cache 接住；当前没有保存任何建议。这是后端程序运行时内存中的值，未写 PostgreSQL，也不是浏览器的 buffer。
2. ticket_text = ...：变量接住完整工单文字字符串，其中 \n 表示换行。内容仍是“标题：打印机无法连接”和“状态：open”两行。此示例把这份完整文字作为查找名称，正式业务缓存条件稍后单独设计，不把这个示例当完整缓存键方案。
3. 第一次 .get(ticket_text)：先取变量中的实际字符串，再交给字典查找。当前 advice_cache 为空，所以 get 返回 None，由 cached_advice 接住。None 表示本字典中暂时没有对应保存值，不是 AI 失败，也没有发出 AI 请求。
4. advice = {...}：创建含 summary、next_steps、missing_info 的完整示例字典，由 advice 接住。真实流程中该字典来自 parse_ticket_advice 的返回值；这里直接写出来仅为了观察缓存，不假记格式检查已实际执行。
5. advice_cache[ticket_text] = advice：左边指定“在这个字典里，以完整工单文字为名称的位置”；右边读取 advice 保存的字典并将其关联到该名称。这里方括号在等号左侧，是写入，不是之前等号右侧那种读取。不能因该名称此前不存在就推断写入会 KeyError。
6. 第二次 .get(ticket_text)：同一个查找名称已经有保存值，因此返回那份建议字典，仍由 cached_advice 接住。cached_advice 原来是 None，现在重新指向该建议；读取本身不调用 AI、不改工单状态，也不自动更新网页。

写入后数据形状示意：

```python
{
    "标题：打印机无法连接\n状态：open": {
        "summary": "打印机无法连接，原因待确认。",
        "next_steps": ["检查打印机电源和连接状态。"],
        "missing_info": ["打印机型号和连接方式。"],
    }
}
```

外层字典保存“用哪份资料查哪份建议”；内层字典才是最终三栏建议。不是把整份建议变成字符串，也不是把工单写入数据库。

### 条件变化的一个具体例子

如果状态由 open 变为 in_progress，新的工单文字为“标题：打印机无法连接\n状态：in_progress”。它与原查找名称不是同一个字符串。在本示例中，用新文字 get 会得到 None，旧条目仍在字典中，只是不匹配新名称。

缓存未命中不等于已删旧值；给变量换值也不会自动查数据库、请求模型或刷新页面。正式代码必须把“取不到就生成”“成功后保存”“命中就发 done”连接起来才会产生业务效果。

本课起步采用后端进程内存的思路；重启不会保留这份字典，多个后端进程也各自持有。当前只理解这一保存位置，不新增 Redis、数据库表或其他运行服务。
