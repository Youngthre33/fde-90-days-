# Day132：观察旧页面保存怎样覆盖先前修改

## 本课解决的问题

两个人先看到同一张工单的旧标题。A 先保存自己的标题，B 没有重新读取，随后用自己基于旧标题写出的新标题保存。现有更新语句只用编号定位工单，没有检查“用户上次看到的内容是否已经变化”，因此后一次保存可以覆盖前一次保存。今天只复现和读懂现象；Day133 再学习阻止旧页面覆盖的办法。

## 实际环境与操作顺序

- 在 pgAdmin 中使用两个指向同一 `ticket_app_test` 数据库的 Query Tool 标签，分别当作 A、B。它们模拟两个操作者，不是两个数据库，也不需要同时按执行键。本课不操作日常库 `ticket_app`。
- A 在 `public.tickets` 创建专用练习工单：

  ```sql
  INSERT INTO public.tickets (title)
  VALUES ('Day132: 原始标题')
  RETURNING id, title, status;
  ```

  学习者截图显示新工单 `id = 5`、`status = 'open'`。之后所有修改都限定 `WHERE id = 5`。
- A、B 分别先运行 `SELECT id, title, status FROM public.tickets WHERE id = 5;`，都以原始标题为自己看到的旧内容；随后 B 不重新查询。A 先执行：

  ```sql
  UPDATE public.tickets
  SET title = 'Day132: 原始标题 + A补充'
  WHERE id = 5
  RETURNING id, title;
  ```

- B 仍按先前看到的原始标题执行：

  ```sql
  UPDATE public.tickets
  SET title = 'Day132: 原始标题 + B补充'
  WHERE id = 5
  RETURNING id, title;
  ```

- 最后 A 重新查询 5 号。学习者的最终查询截图及回复显示标题留下的是 `B补充`，状态仍为 `open`。A、B 两次 `UPDATE RETURNING` 的单独输出未贴出，不能把它们记为额外截图证据。

## 为什么会覆盖

关键时间顺序：两边上次显示“原始标题” → A 保存后数据库实际为 `A补充`，B 窗口仍显示上一次查到的原始标题 → B 的 `UPDATE` 只检查 `id = 5`，此时编号仍存在，所以把当前标题写成 `B补充`。B 的旧值停在屏幕上的查询结果中，不是 PostgreSQL 一直冻结给 B 的数据库状态。现有 `ticket_repository.py` 的标题更新同样只写 `WHERE id = %s`；本课在 pgAdmin 直接执行 SQL，没有实际测试网页的多人操作。

## 理解题与补讲

1. 学习者最终查询确认 `B补充`。问“B 执行前数据库中是什么”，初答把最终值 `B补充` 提前放到执行前，并提到幂等性；讲评后能说出 B 执行前数据库已是 `A补充`，执行后才是 `B补充`。幂等性讨论同一操作重复执行，不是本例两种标题先后覆盖的原因。
2. 学习者正确指出 A 的 `RETURNING` 只能说明 A 保存时的结果，不能证明 B 保存后 A 的标题还在；需要再 `SELECT`。
3. 对“A 保存后 B 屏幕会显示什么”的迁移检查，学习者一度把 B 屏幕也说成 `A补充`。补讲数据库当前行与 B 上次查询结果是两个位置后，学习者明确回答：B 不操作不会自动变，重新查询才会看到 A 的修改。此处理解已纠正。
