# Day129：每项测试使用独立的临时 schema

## 本课解决的问题

Day128 的最小测试直接写入 `ticket_app_test` 的 `public` 表；即使后面的 `assert` 失败，已经提交的工单也不会自动撤销。本课让 pytest 为每项测试准备独立的临时 schema，测试结束后删除整个 schema。

## 实际文件与流程

- `ticket_app/tests/conftest.py`：pytest 自动读取的准备与清理文件。`@pytest.fixture(autouse=True)` 让 `isolated_database` 在每项测试前运行。新增数据库名检查：只有 `settings.db_name == "ticket_app_test"` 才继续。
- `ticket_app/tests/test_day129_isolation.py`：两项对称测试。每项先断言当前临时表为空，再创建一张工单并按返回编号重新查回。
- fixture 在 `yield` 之前生成随机 `schema_name`、创建 schema、读取 `schema.sql` 在其中建表，并用 `monkeypatch` 临时把 `ticket_repository.get_connection` 指向 `connect_to_test_schema`。
- `yield` 把执行权交给 pytest 运行当前测试。测试结束后，`finally` 检查随机名称的格式，执行 `DROP SCHEMA ... CASCADE`；pytest 随后恢复临时替换的连接函数。

## 观察到的结果

- 学习者截图：PowerShell 配置检查打印 `ticket_app_test`；pytest 收集两项测试，两项均 `PASSED`，汇总为 `2 passed in 1.45s`。
- 学习者报告：在 `ticket_app_test` 的 pgAdmin Query Tool 查询符合本课命名规则的临时 schema，结果为 0 行。
- 两项测试通过证明各项测试开始时看到空表并能创建、查回自己的工单；单靠 `2 passed` 不能证明旧 schema 已删除。临时 schema 查询的 0 行为本次清理提供了额外观察证据。

## 关键理解与讲评

- 学习者能说明：如果第一项的 schema A 意外残留，第二项仍可能使用新的空 schema B 而通过。因此两项测试通过与旧 schema 已清理是不同结论。
- 对“`with connect_to_database()` 负责删除、失败会回滚到 `with` 开始”的初答已补清：`finally` 安排收尾；连接函数建立连接；真正删除的是 `connection.execute(...)` 中的 `DROP SCHEMA ... CASCADE`；删除成功后退出 `with` 会提交这次删除。已提交的 `INSERT` 不因后续 `assert` 失败而回滚。
- 学习者随后正确回答迁移情境：不执行 `DROP SCHEMA` 时，已提交的工单会留在临时 schema；执行成功后数据消失，是因为整个临时 schema 被删除，而不是回滚。
