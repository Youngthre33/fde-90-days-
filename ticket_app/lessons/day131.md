# Day131：给状态列表查询建立索引，并读执行计划

## 本课的实际用途

工单列表查询会用 `WHERE status = ...` 筛选，再用 `ORDER BY id` 排序。索引是 PostgreSQL 在工单表之外维护的查找目录，可能减少大量数据时的查找工作；筛选条件仍由 SQL 的 `WHERE` 决定。索引需要额外存储，并在对应表新增、修改或删除记录时维护，不是每条查询都会选用。

本课只在 pgAdmin 的 `ticket_app_test` 数据库、`public.tickets` 表练习。它不是日常库 `ticket_app`，也不是 Day129/130 每项 pytest 创建后又删除的随机临时 schema。

## 操作与观察

1. 在 pgAdmin Query Tool 运行 `SELECT current_database() AS db_name, COUNT(*) AS ticket_count FROM public.tickets;`。学习者反馈目标检查没有问题；未提供具体行数，不补记数字。
2. 查询 `pg_indexes` 中 `schemaname = 'public' AND tablename = 'tickets'` 的索引。操作前截图只有 `tickets_pkey` 一行：它是 `id` 主键已有的索引，不需要重复给 `id` 建索引。
3. 对 `SELECT id, title, status FROM public.tickets WHERE status = 'open' ORDER BY id LIMIT 10` 执行 `EXPLAIN`。操作前截图显示 `Seq Scan on tickets` → `Filter: status = 'open'` → `Sort Key: id` → `Limit`。按数据产生顺序从计划树底部向上读。
4. 学习者在测试库执行：

   ```sql
   CREATE INDEX IF NOT EXISTS day131_tickets_status_id_idx
   ON public.tickets (status, id);
   ```

   `(status, id)` 对应先按状态筛选、再按编号排序。`IF NOT EXISTS` 只避免同名索引的重复创建报错，不替代核对索引定义。
5. 用完全相同的 `EXPLAIN` 再看一次。截图仍是 `Seq Scan`、`Filter`、`Sort`、`Limit`，所以这次计划没有选择新索引。前后 `cost` 与 `rows` 的估计数字不同；它们不是实测耗时或实际返回行数，不能据此宣称索引让查询加速。当前截图不足以确定估算变化的具体原因。
6. 再次查询 `pg_indexes`。学习者截图显示两行：新索引 `day131_tickets_status_id_idx` 和原有 `tickets_pkey`。这分别确认“索引存在”和“当前计划没使用它”，两件事并不矛盾。截图结果列宽截断了部分 `indexdef`，建索引 SQL 如上记录。

## 两道理解题的实际讲评

1. 对“`cost` 从约 20 降到约 1，证明索引使本次查询变快”不同意，理由是数据库并非每次都走索引、不能靠估算量确认。补充本例最直接的证据：两张执行计划都写着 `Seq Scan`；`cost` 不是实测秒数。理解方向正确。
2. 正确指出日常库 `ticket_app` 新增工单不会维护本课索引，因为它建在独立的 `ticket_app_test.public.tickets` 上。只有对这张测试表进行写入时，PostgreSQL 才需维护这份索引。

## 范围、Git 与下一课
