## 1. 今天解决什么问题

Day120已经让Swagger通过8001查询PostgreSQL。Day121让普通工单网页完成同样的读取：浏览器先从5500取得HTML和JavaScript，再由浏览器里运行的JavaScript向8001请求工单；8001后端通过5432查询PostgreSQL，最后把数组返回给浏览器显示。

今天只看读取列表。页面虽然已有添加、编辑、状态、删除按钮，但对应写操作留给Day122—124，不在本课点击或展开代码。

本机练习中的三个入口：

| 入口 | 后面的程序 | 本课负责什么 |
| --- | --- | --- |
| 5500 | Python静态文件服务 | 把index.html、main.js等网页文件交给浏览器 |
| 8001 | Uvicorn运行的FastAPI后端 | 接收GET /tickets，组织查询并返回JSON |
| 5432 | PostgreSQL数据库服务 | 接收后端发来的SQL，查询真实工单数据 |

浏览器不会直接连接5432，也拿不到数据库密码。5500也不会代替后端去查数据库：浏览器从5500取得JavaScript后，由JavaScript直接向8001发请求。

未来真实项目中，三个角色通常仍然存在，但可能分别部署：网页文件可放在Web服务器或静态托管服务，后端API在应用服务器，PostgreSQL在内网数据库服务器或托管数据库。本机练习把它们放在同一台电脑上，用不同端口区分。

## 2. 浏览器从哪里取得JavaScript

现有文件：`C:/Users/Administrator/Documents/GitHub/fde-90-days-/ticket_app/web/index.html`。末尾是：

```html
<script type="module" src="main.js"></script>
```

- script告诉浏览器加载并运行JavaScript。
- type="module"说明main.js使用模块写法，可以通过import从其他.js文件取得名称。
- src="main.js"表示文件与index.html位于同一目录。
- 这行由浏览器执行，不是PostgreSQL执行。它只把main.js加载进页面，还没有说明API地址。

网页必须通过5500打开；不要双击HTML成为file://地址，也不要把127.0.0.1换成localhost。当前后端CORS明确允许的网页来源是`http://127.0.0.1:5500`。

## 3. API地址来自哪里

现有文件：`ticket_app/web/constants.js`第27行附近：

```javascript
const TICKETS_API_URL =
    "http://127.0.0.1:8001/tickets";
```

- const创建一个之后不重新指向其他值的名称。
- TICKETS_API_URL是我们起的名字，表示工单接口地址。
- 等号把右边的地址字符串交给左边名称。
- 127.0.0.1指当前电脑；8001找到后端；/tickets找到工单列表接口。
- 分号结束这条JavaScript语句。

文件末尾把它导出：

```javascript
export {
    TICKETS_API_URL
};
```

export让其他JavaScript模块可以导入这个名字。main.js顶部现有import列表取得了TICKETS_API_URL，所以后面不需要重复写完整地址。导入地址不会自动发送请求。

## 4. 第一小段：开始加载并发送GET

现有文件：`ticket_app/web/main.js`第377行附近。函数开头：

```javascript
async function loadTicketsFromApi() {
    try {
        reloadButton.disabled = true;
        renderLoading();

        const response =
            await fetch(TICKETS_API_URL);
```

- async function定义一个可能需要等待网络结果的异步函数；函数名可读成“从API加载工单”。定义本身不执行。
- try开始执行可能失败的加载步骤；如果里面发生错误，后面的catch负责处理。
- reloadButton.disabled = true把重新加载按钮设为不可点，避免当前请求未完成时反复点击。
- renderLoading()调用已有显示函数，把页面数量文字改成“正在加载工单...”，并清空旧列表。
- const response声明名称response，用来接住这次HTTP响应对象。
- fetch(TICKETS_API_URL)由浏览器向`http://127.0.0.1:8001/tickets`发GET请求。没有写method时，fetch默认使用GET。
- await让当前异步函数在这里等响应回来，再把响应对象交给response；不是让整个电脑停止工作。

response代表完整HTTP响应，里面有状态码、响应头和响应正文等信息。它还不是解析后的工单数组。

## 5. 第二小段：检查响应、取得数组

```javascript
        if (!response.ok) {
            throw new Error(
                `请求失败,HTTP状态码:${response.status}`
            );
        }

        const loadedTickets =
            await response.json();
```

- response.ok在HTTP状态码为200—299时为true。
- 前面的感叹号!表示“不是”；因此if条件是“如果响应不成功”。
- throw new Error主动产生一个JavaScript错误，停止try中的正常流程，转到catch。
- 反引号包住可插值文字；`${response.status}`把实际HTTP状态码放进错误说明。
- const loadedTickets创建名称，用来接收真正的工单数据。
- response.json()读取响应正文，并把JSON转换成浏览器可用的JavaScript数据；本接口返回的是工单数组。
- await等待正文转换完成，再把数组交给loadedTickets。

例如返回正文可能是：

```json
[
  {"id": 1, "title": "某个标题", "status": "open"},
  {"id": 2, "title": "另一个标题", "status": "in_progress"}
]
```

实际标题和状态以数据库当前内容为准。不要把例子文字当成真实数据库结果。

## 6. 第三小段：保存到浏览器内存并显示

```javascript
        setTickets(loadedTickets);

        render(
            loadedTickets,
            editingId
        );

        return loadedTickets;
```

- setTickets(loadedTickets)把API返回的数组交给data.js中的tickets变量，更新浏览器当前使用的数据。它只改变浏览器内存，不执行SQL，也不修改PostgreSQL。
- render(...)调用页面显示函数。
- 第一个参数loadedTickets是要显示的数组；第二个参数editingId表示当前正在编辑哪张工单，本次初始值为null，即没有工单处于编辑状态。
- render会更新“当前有X个工单”的文字，并为数组中的每张工单生成页面列表项。
- return loadedTickets把数组交回调用这个加载函数的位置；页面启动时的调用没有用变量接住这个返回值，页面显示依靠前面的setTickets和render已经完成。

data.js中原来有两条本地示例数据。API成功返回后，setTickets会用真实返回数组替换浏览器内存中的示例；所以页面出现两条示例文字不能证明PG读取成功，应该看后端请求是否成功以及显示内容是否与PG对应。

## 7. 第四小段：失败和收尾

```javascript
    } catch (error) {
        console.error(
            "工单加载失败:",
            error.name,
            error.message
        );

        renderLoadError();
    } finally {
        reloadButton.disabled = false;
    }
}
```

- catch(error)在try中的网络请求、状态检查或数据处理发生错误时执行；error接住错误对象。
- console.error把错误名称和说明写到浏览器开发者工具的控制台，给开发和排错人员看。
- renderLoadError()把页面提示改成“工单加载失败,请稍后重试”，并清空列表。
- finally无论成功还是失败都会执行。
- reloadButton.disabled = false重新启用“重新加载工单”按钮。
- 最后的两个右花括号分别结束finally和整个函数。

文件末尾：

```javascript
loadTicketsFromApi();
```

括号表示真正调用前面定义的函数。浏览器加载main.js后执行到这里，因此页面不用先点“重新加载”按钮，也会自动请求一次工单列表。

## 8. 为什么网页可能显示10张，而数据库有12张

后端GET /tickets现有参数中，`limit`默认10、`page`默认1、`order`默认asc。浏览器请求地址没有另外提供这些参数，所以这次取得按id升序的第一页，最多10张。

教师本轮只读核对：PostgreSQL当前有12张工单，默认API实际返回id 1—10共10张。因此网页预期显示“当前有10个工单”。这里的10是本次loadedTickets数组长度，不是数据库总数；其余数据没有被删除。分页的进一步操作不在本课扩展。

## 10. 本课完整流程

浏览器向5500请求index.html和JavaScript → 5500返回文件 → 浏览器运行main.js → 文件末尾调用loadTicketsFromApi → fetch向8001发送GET /tickets → 后端main调用service → service调用repository → repository经5432向PostgreSQL发送SELECT → PG返回第一页工单 → 结果逐层回到8001响应 → 浏览器response.json得到loadedTickets数组 → setTickets更新浏览器内存 → render更新网页。

5500只提供网页文件；8001处理业务请求；5432查询数据库。响应回来后，页面显示动作发生在浏览器里。

## 13. 原答讲评与一次复核（2026-09-28）

学习者原答：“不能，他们是一层套一层设置好了的，不能跳过，并且端口也设置好了；2 set是改变内存的工单数量，刷新网页的时候是render.js在工作然后控制网页刷新。”

第1题结论正确，理由只对一部分。5500不能查PG的根本原因是它当前只是静态文件服务：只认识目录里的文件，没有FastAPI的`/tickets`路由、repository函数、psycopg连接和数据库账号。端口不是永远固定的数字，配置一致时可以更换；即使把静态文件服务改到别的端口，它也不会自动获得后端能力。当前流程也不是5500把请求层层转交给8001：浏览器取得JavaScript后，JavaScript直接向8001发送GET。

第2题前半方向正确。`setTickets(loadedTickets)`替换的是浏览器内存中的工单数组，页面数量只是render根据`loadedTickets.length`算出的显示结果；它不只改数量，也不会改PG。刷新整张网页时，浏览器先重新向5500取HTML/JS，浏览器执行main.js，文件末尾再次调用`loadTicketsFromApi()`，其中fetch重新向8001取得数据；`render.js`只把已经取得的数组显示成数量和列表，不负责从数据库或API取数据。

本轮现场只读检查：127.0.0.1:5500、127.0.0.1:8001、5432均监听；5500根路径和main.js均返回200，8001/tickets返回200和允许`http://127.0.0.1:5500`的CORS响应。教师未启停这些用户进程，未修改数据。该证据说明文件服务和API在线；未通过工具直接观察浏览器DOM，页面具体显示仍以学习者现场为准。
