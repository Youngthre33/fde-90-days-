## 第一小段：本机Python发出一次请求

用途：以后后端调用另一个系统，也需要主动发送HTTP请求。本段先把请求方放在Windows本机，响应方沿用上海服务器的既有health接口，以便分清两边；从这个本机Python程序的角度，对方是外部服务，不要求先找另一个陌生网站。

教师已新增ticket_app/check_remote_health.py，内容如下。它是手动运行一次的客户端脚本；不是FastAPI新接口，也不是后台监控。后续在同一文件上继续学习。仓库requirements.txt已经列有httpx==0.28.1；本轮没有运行Python导入验证或安装依赖，不能仅凭清单称用户环境已验证。

```python
import httpx

url = "https://42.192.114.83/health"

response = httpx.get(url, timeout=5.0)

print("状态码：", response.status_code)
print("响应正文：", response.text)
```

逐行解释：

- import httpx：本机Python导入发送HTTP请求的库；可用已学浏览器fetch作功能类比，但执行者和运行位置不同。
- url = ...：url变量保存完整地址字符串；赋值本身不发送请求。目标是上海服务器公开HTTPS入口下的/health，不是本机127.0.0.1。
- httpx.get(...)：调用库的get函数，按第一个参数中的地址发送GET，进行连接、发送和接收；同步调用在等待时不会先执行后面的print。这里没有await，不展开并发模型。
- timeout=5.0：给函数传一个命名参数，数值单位是秒；把HTTPX的连接/读/写/连接池等待等操作的超时值设为5秒。它不是强制请求等待5秒，也不是整段HTTP请求总耗时严格最多5秒；例如读超时限制等待下一块响应数据的时间，不是完整下载总时长。HTTPX本身默认已有5秒超时，本段显式写出便于理解和后续修改，不能说原来默认会永久等。
- response = ...：先计算等号右边；成功收到响应后，HTTPX在本机返回Response对象，变量response接住；它包含状态码、响应头、正文，不只是正文字符串。如果发生未捕获的超时/连接异常，这次赋值不会正常完成，后续print也不会运行。
- response.status_code与response.text：点号读取响应对象属性，分别得到HTTP状态码和解码后的正文文本；print把标签与对应值显示在运行脚本的本机终端。text中的JSON目前只是文本，不是已转换成Python字典。

网络错误与错误HTTP响应要分清：本段没有调用raise_for_status，若服务器正常发回404/500，get通常仍会返回Response并打印相应状态/正文；不能把所有非200结果都叫超时。后续讲异常和有限重试时再逐段展开。

## 2026-10-09 第二小段：捕获HTTPX超时，观察代码跳转

用户紧接运行步骤回复“问题继续”“没问题”，结合上下文按用户报告记录第一小段正常请求完成，没有原始输出/教师独立请求验证。继续在同一check_remote_health.py加try/except，不新增文件或部署；教师尚未运行正常/超时分支。

现行脚本：

```python
import httpx

url = "https://42.192.114.83/health"

try:
    response = httpx.get(url, timeout=5.0)
    print("状态码：", response.status_code)
    print("响应正文：", response.text)
except httpx.TimeoutException:
    print("请求超时：本次网络等待超过了设置的限制。")

print("本次检查结束。")
```

try后冒号引出尝试执行的缩进代码块，不表示重试。正常时依次执行GET赋值和两个print，跳过except。若httpx.get在某网络等待操作超过限制，HTTPX抛超时异常，不正常返回Response，本次response赋值不会完成；try剩余两个print跳过，Python寻找匹配的except。

except与try同级，httpx.TimeoutException是HTTPX超时异常的基类，匹配例如ConnectTimeout/ReadTimeout。当前不展开继承实现，只说明异常类别；不是HTTP状态码，也不是服务器返回的一段JSON。没有括号，因为这里是写要匹配的异常类型，不是在调用一个处理函数。冒号后缩进的print由本机Python执行，显示我们自己写的提示。

最后print与try/except同级，位于整个结构之后。正常完成try或超时被except处理后，都会继续执行该行；其它未匹配异常仍可能中止脚本，不能解释为无论任何情况都必执行（它不是finally）。except不会自动重发请求，也不会跳回失败那行，有限重试还未实现。

完整流程：Windows终端启动脚本→try内HTTPX发送GET→正常路线经上海Caddy/Docker/Uvicorn/main.py中间件/get_health→HTTP响应回本机HTTPX→返回Response/赋值→状态与正文print→跳过except→最后结束提示。超时路线在本机HTTPX等待超限时抛异常→跳过本次赋值及try中后续print→匹配except→打印超时提示→结束提示。本机超时不证明上海没有收到或处理请求；服务器已完成但响应传回途中延迟也可能使调用方超时，不保证撤销服务端动作。

对照Day147：数据库停止后服务器返回500，本机若正常收到这个HTTP响应，它仍是Response。当前只调用get，没有raise_for_status，500不会因状态码本身进入TimeoutException分支。连接被立即拒绝、证书错误等通常也不属超时类别，仍按真实异常处理，后续需要时再解释。

用户操作（本机Windows，不是Ubuntu）：先保持timeout=5.0，使用既有项目.venv运行模块，正常预期三行：状态码200、响应正文status:ok、检查结束。随后仅在该文件把5.0临时改成0.001（1毫秒）并保存，再运行一次；公网请求通常更易触发ConnectTimeout/ReadTimeout，预期超时提示+检查结束，但此方法不保证所有环境一定超时，若仍200或不同错误如实报告，不反复调整成额外实验。观察后恢复5.0、保存并运行一次确认恢复。超时测试不停止数据库/Caddy，不绕过证书验证。

反馈只需正常时是否三行、1毫秒是否超时提示且最后继续、恢复5.0是否正常；异常取实际末尾。第二小段实际输出仍待，不预记超时分支或恢复成功。下一小段再加有限次数/间隔和适用范围，整课后两题；Day147限定Git、本课Git仍待。

## 2026-10-09 第三小段：最多尝试三次，仅超时且有剩余机会才重试

用户在上一段正常/1毫秒超时/恢复步骤后报告“没问题，继续往下”，按用户反馈记录第二小段及恢复正常完成，未提供原始输出或教师独立验证。定向读取实际脚本，timeout已由用户恢复为5，与此前5.0同为5秒设置，保留其写法。不能据此预记有限重试理解与操作。

在同一check_remote_health.py加入from time import sleep、max_attempts=3和for循环，现行完整代码：

```python
from time import sleep

import httpx

url = "https://42.192.114.83/health"
max_attempts = 3

for attempt in range(1, max_attempts + 1):
    print("第", attempt, "次请求")
    try:
        response = httpx.get(url, timeout=5)
        print("状态码：", response.status_code)
        print("响应正文：", response.text)
        break
    except httpx.TimeoutException:
        print("请求超时：本次网络等待超过了设置的限制。")
        if attempt == max_attempts:
            print("已达到最大尝试次数，本次检查失败。")
            break
        print("等待1秒后重试。")
        sleep(1)

print("本次检查结束。")
```

按小块讲，完整代码放文件中，不先倾倒整页陌生语法。第一块：sleep来自Python标准库time，用于让当前脚本暂停1秒；不是让上海服务器暂停，也不是timeout参数。max_attempts表示总尝试次数3，包含第一次，因此最多额外重试2次，不是1+3。

第二块：range(1,max_attempts+1)在本例为range(1,4)，提供1、2、3，不包含4；for每轮把当前数交给attempt，执行其缩进块。print三个参数在终端显示当前次数。try内请求的成功返回路线与上一段相同，正常收到HTTP响应并打印后，break跳出最近的for循环，直接来到循环外的检查结束；break不是退出try之后继续下一轮，也不是结束整个Python进程。404/500正常返回也会打印并break，因为本脚本没有raise_for_status，停止重试不等于HTTP业务成功。

第三块：except仅接HTTPX超时。attempt == max_attempts是比较，区别于单个等号赋值；最后一次超时后打印失败并break，跳过本块之后的等待，不发第4次。未达上限时，if不执行，继续等待提示和sleep(1)；本轮代码块走完，for自动取下一数，从顶部再次执行。sleep本身不发请求，也不把代码跳回去，下一次请求由for下一轮调用httpx.get发出。连续三次超时仅有两次sleep。非超时异常仍未捕获，不能宣传所有网络失败都会重试；当前只读health演示不作为完整生产重试策略。

逐次执行示例：第1轮本机HTTPX等待超限→except→次数1不等3→sleep1秒；第2轮同理；第3轮超时→次数3等3→失败提示/break→循环外结束。若任意一轮正常返回响应，则在try中break，后续轮不再执行。结束提示只表示代码走到了末尾，不证明服务健康。

完整请求路线仍是本机循环每轮httpx.get→上海Caddy443→服务器8002/Docker api8001→Uvicorn/FastAPI中间件/get_health→HTTP响应回本机HTTPX→当前这轮response变量→打印/break。每轮httpx.get是新请求；超时不保证上一轮服务器没有执行或完全停止，不能当成原请求继续等待。此接口不访问数据库，重复GET health不会创建工单。

重试边界用项目新增工单例子衔接：客户端POST后服务器可能已经入库，只是响应返回途中出问题；客户端超时再发一次可能创建两张。当前循环只围绕固定GET health，不直接套到POST；未来写操作要考虑如何防止重复执行，到对应课再实现，不扩展成幂等键新课。

用户操作同一本机.venv命令：先保持timeout=5正常运行，预期第1次请求/200/正文/检查结束后停止；临时只将timeout=5改0.001，运行一次，若每轮均超时则出现1/2/3次、两次等待、最大次数提示且没有第4次；某轮实际成功就应当提前结束，不为凑满3次盲改网络。随后恢复timeout=5、保存并运行确认正常。不要改max_attempts、服务、凭据或证书。教师本轮只写入代码并静态阅读，未运行网络请求或新测试，三种操作结果均待反馈。
