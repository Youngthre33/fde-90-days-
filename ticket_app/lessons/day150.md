## 为什么用公网IP证书

Let’s Encrypt在2026-01-15正式提供公网IP证书，要求shortlived profile，证书有效160小时，必须自动续期。Caddy2.11系列已支持，官方stable安装避免Ubuntu旧包拒绝IP。IP默认内部CA不能让普通浏览器直接信任，所以明确指定Let’s Encrypt ACME issuer与shortlived；不用忽略证书错误或明文HTTP传员工token。

只查看入口配置：

```caddyfile
{
    default_sni 42.192.114.83
}

42.192.114.83 {
    tls {
        issuer acme https://acme-v02.api.letsencrypt.org/directory {
            profile shortlived
        }
    }
    reverse_proxy 127.0.0.1:8002
}
```

外层IP指定这个站点的公开地址；tls是浏览器到Caddy的HTTPS设置，issuer指定申请证书的机构接口，shortlived是IP证书类型，不是员工登录token。default_sni为无SNI的IP访问指定证书选择默认值：云网卡可能只有10.0.0.8私网地址，不能按本地私网IP误选证书。reverse_proxy由Caddy在服务器执行，127.0.0.1指上海服务器自身，8002由Docker转给api内Uvicorn8001；请求路径如/web/和/tickets保留。

网页仍由main.py的app.mount读取web/index.html，浏览器按script加载main.js及模块并在Windows执行。constants.js的/tickets从当前https://42.192.114.83/web/解析为https://42.192.114.83/tickets；fetch带Authorization交Caddy→Docker→Uvicorn/FastAPI→auth.py认证/权限→main.py业务路由→service→repository→PostgreSQL。数据沿函数return回路由/框架JSON→Caddy HTTPS响应→原fetch的await→response.json→页面渲染。认证与数据存放位置不因为入口改变而换到Caddy或浏览器。

## 用户操作完整流程（实际执行尚待反馈）

先在腾讯云上海轻量实例防火墙检查并仅添加缺失的TCP80、TCP443允许入站，来源0.0.0.0/0。22保持，8001/8002/5432/5433不需要放通公网。80用于证书验证及跳转，输入token始终从https://地址开始；云防火墙与Ubuntu防火墙是两个位置。

Windows管理窗口普通SSH登录42.192.114.83，在Ubuntu执行`mkdir -p /home/ubuntu/ticket-app/public-entry`。Windows另一个PowerShell窗口使用scp一次上传deploy目录中的三个文件到该目录；小文件传完无需重建镜像、重传tar或读取.env。

回到Ubuntu管理窗口运行：

```bash
sudo systemd-run --unit=ticket-public-entry-setup --description="Ticket app HTTPS setup" /bin/bash /home/ubuntu/ticket-app/public-entry/setup-public-entry.sh
```

sudo将这一次安装交给服务器systemd管理，不将后台任务绑定SSH窗口。unit只是后台任务名，安装后常驻网页服务名为caddy。需要查看进度时执行`sudo journalctl -u ticket-public-entry-setup --no-pager -n 60`。窗口断开可重新普通SSH登录后继续读同一任务日志，不先重复启动同名任务或重传镜像。

安装输出HTTPS_READY才表示服务器本地用受信任证书的验证通过；Caddy首次签发也依赖云端80/443放行、服务器出站能到ACME，不能把systemctl active当作证书已就绪。后台脚本若遇已有网站或配置会停下要求据输出检查，不覆盖未知服务。脚本不能代修改腾讯云防火墙。

浏览器验收：直接打开https://42.192.114.83/health，证书无警告且status:ok；打开/web/，填已有员工凭据加载既有工单，实际查询检验DB链路。然后关闭旧SSH转发窗口Ctrl+C，仍可刷新新HTTPS网页与查询，才确认新入口独立。不要忽略证书警告后输入token；health成功不单独证明数据库正常。

VPN分流按客户端实际能力操作：若支持自定义目标，将42.192.114.83/32设DIRECT/直连，覆盖该目标所有端口，Codex保持既有代理策略；若仅有智能/绕过大陆模式，需要根据实际规则/连接显示核对是否命中，不能仅凭名字认定。若客户端只支持全局VPN且无目标例外，则需要支持分流的客户端或配置，服务器不能控制Windows选择的VPN路线。
