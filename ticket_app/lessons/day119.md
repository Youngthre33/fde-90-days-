```python
import psycopg

from ticket_app.config import settings


def create_ticket(title):
    with psycopg.connect(
        host=settings.db_host,
        port=settings.db_port,
        dbname=settings.db_name,
        user=settings.db_user,
        password=settings.db_password,
        connect_timeout=5,
    ) as connection:
        cursor = connection.execute(
            "INSERT INTO tickets (title) VALUES (%s) RETURNING id, title, status",
            (title,),
        )
        row = cursor.fetchone()

    print("连接是否已关闭：", connection.closed)

    return {
        "id": row[0],
        "title": row[1],
        "status": row[2],
    }


if __name__ == "__main__":
    ticket = create_ticket("Day119：with成功提交")
    print("新增结果：", ticket)
```

## 4. 按顺序解释

import psycopg导入Python连接PostgreSQL所用的库；from ticket_app.config import settings取出已经配置好的连接信息。它们自己没有建立连接。

def create_ticket(title):定义新增函数，调用时传来的标题交给title。括号列参数，冒号后的缩进是函数内容。

with psycopg.connect(开始调用connect，下面参数与Day118相同：host是服务地址，port是服务入口，dbname是数据库名称，user是数据库账号，password是该账号密码，connect_timeout=5是本次建立连接的超时设置，不是5秒后自动断开。settings.xxx读取对应配置；参数中的等号把读取的值交给指定参数。

) as connection:中的右括号结束connect调用；connect真正建立连接并返回一个连接对象；as connection让函数中用connection这个名字操作这次连接，不是又建立一个连接。冒号引出with管理的缩进部分。

本课使用Psycopg 3的默认连接方式：with里的操作正常结束时，连接对象提交本次修改，再关闭连接；如果异常离开这段，则回滚本次尚未提交的修改并关闭，错误仍向外报告。具体行为来自Psycopg连接对象，不是所有with都自带数据库功能。此前SQLite连接的with不会自动close，所以两种代码收尾不一样。

cursor = connection.execute(通过刚建立的连接发送SQL，返回一个cursor供Python取得结果。下一行SQL：向tickets的title列新增一行；%s的位置使用下一行(title,)提供的值；RETURNING要求PostgreSQL将该行的id、title、status返回。元组中逗号说明只有一个参数；右括号结束execute调用。

row = cursor.fetchone()读取这次返回的一行，放入row。此时还在with里面，取到结果不等于已经提交。

下一行print与with对齐，比row行少一级缩进：这说明已经离开with。Python先完成with的退出处理，再执行print；正常情况下提交与关闭已经完成。这就是不用再单独写commit和finally/close的位置依据。

print("连接是否已关闭：", connection.closed)在终端显示连接的关闭状态。closed是状态属性，不是方法，不加括号；True表示本次Python连接已关闭，PostgreSQL服务仍运行，pgAdmin自己的连接不受影响。连接对象仍可用于读取closed状态，不能再通过它执行SQL。

return后面的花括号创建字典。"id"、"title"、"status"是三个键，冒号右侧分别使用row的第0、1、2项。row在fetchone时已取到Python内存中，关闭数据库连接不会清空它。return把字典交给调用处；这里的return在with外，保存与关闭已经发生。

if __name__ == "__main__":使下面示例只在直接运行本模块时执行。ticket = create_ticket("Day119：with成功提交")提供标题并接住返回字典；最后print显示字典。标题是用于识别本次练习的文字，没有特殊功能。

## 6. 第二步：新增之后，下一步失败

目的：观察INSERT已经执行并返回编号，但这一组操作还没完成时出错，数据库会不会留下半成品。现实中新增工单后还可能要保存一条处理记录；本课用一行主动报错代表后续步骤失败，不增加新表或功能。回滚在这里就是取消本次尚未提交的数据库修改，不是删除之前已保存的所有工单。

仍在create_ticket.py里操作。教师保持正常源文件不变，下面两处临时修改由学习者跟随完成。

第一处，在row = cursor.fetchone()下面加两行，三行保持相同缩进，都在with里面：

```python
        row = cursor.fetchone()
        print("本次尚未提交的编号：", row[0])
        raise RuntimeError("Day119：模拟后续步骤失败")
```

- row = cursor.fetchone()是原有行，取得PostgreSQL返回的新工单信息，不重复添加。
- print括号里先给提示文字，再给row[0]。下标0取这一行第一项，也就是新id。打印只是在终端显示，不提交。
- RuntimeError是Python自带的一种错误类型，不需要新增import；括号中的文字说明这次模拟的错误。
- raise主动抛出这个错误，打断当前正常执行。故意放在INSERT和fetchone之后，确保演示的是“前一步做过了，后一步失败”。

第二处，文件底部调用的标题临时改成：

```python
    ticket = create_ticket("Day119：模拟失败")
```

只是换传进函数的标题，方便辨认练习。其他连接设置、SQL、return都保留。

在VS Code项目终端运行一次：


预期先打印本次尚未提交的真实编号，然后终端显示错误经过，末尾为RuntimeError: Day119：模拟后续步骤失败。Traceback就是Python列出的错误发生位置和调用经过。这个预期错误来自刚加的raise，不是要求重新配置数据库。

流程是：函数接收标题 → connect连接 → INSERT执行 → fetchone取到行 → print显示编号 → raise产生错误 → 带着错误离开with → Psycopg连接回滚并关闭 → 错误继续向外报告。本课没有在with内部处理掉这个错误。

with外面的“连接是否已关闭”那行print和return不会执行。不是连接没有关闭，而是退出with的收尾已经完成，随后错误继续向外传播。调用处create_ticket(...)确实已执行，但没有正常返回字典，所以ticket = ...的赋值未完成，外面的“新增结果”也不会打印。回滚不会抹掉终端之前已经打印的编号。

记下失败那次打印的真实id，在pgAdmin的ticket_app数据库Query Tool按id查。例如终端显示23时才用下面的23；否则换成自己的实际编号：

```sql

```

SELECT选三列，FROM指定工单表，WHERE只找本次失败编号。预期0行：说明这次未提交的新增已被撤回。编号23只是说明写法，不是实际执行结果。

```sql

FROM tickets
WHERE title = 'Day119：with成功提交'
ORDER BY id DESC;
```

回滚只取消本次尚未提交修改，不撤销上次已提交记录。自动编号可能因此跳过一个数字，不能用是否连续判断回滚成败；PostgreSQL序列取出的值不因事务回滚而回收。

观察后删掉临时print和raise两行，保留原row = cursor.fetchone()；将底部标题改回Day119：with成功提交并保存。恢复后不必为确认恢复再执行INSERT。需要静态检查时只编译源码，不导入/运行新增函数。不要把主动报错演示代码留作最终版本。
