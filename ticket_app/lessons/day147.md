# Day147：后端正在运行，不等于数据库已经就绪

## 目标与当前状态

2026-10-09开始本课。Day146的请求编号与日志理解题已通过，用户报告上一轮提交完成。本课只理解两件事：后端能响应与能使用数据库是不同检查；数据库没找到记录与数据库无法连接是不同失败。

本课复用既有业务代码，不新增接口、不重建镜像。用户执行的受控实验会让上海练习库暂时停止，期间工单功能不可用；Docker stop保留容器与数据，start恢复既有容器。整套说明同时给出恢复步骤，不操作down或删除数据卷。教师本轮没有远端执行，全部结果待用户反馈。

## 三个观察位置

- Windows浏览器：https://42.192.114.83/health 和 https://42.192.114.83/docs，发送请求并看响应。
- Windows PowerShell运行普通SSH后，Ubuntu提示符下的命令在上海服务器执行；这是管理连接，不是之前的网页转发。
- 上海api容器运行Python/Uvicorn/FastAPI；db容器运行PostgreSQL。Caddy继续在服务器提供HTTPS入口。

## 先从上一课的请求恢复流程

浏览器GET /health→上海Caddy443→宿主机127.0.0.1:8002→Docker api8001→Uvicorn/FastAPI→main.py的log_request生成编号并调用后续处理→get_health返回status:ok字典→框架形成HTTP响应→中间件增加X-Request-ID→Uvicorn/Caddy→浏览器。get_health没有调用service/repository，因此数据库停止时它仍可返回200。

Swagger Execute带有效员工token请求GET /tickets/{ticket_id}→同样网络入口及中间件→auth.py HTTPBearer/read_token/get_role→main.py get_ticket→ticket_service.find_ticket_by_id→ticket_repository.find_ticket_by_id→get_connection的psycopg.connect访问db:5432→执行SELECT→fetchone取结果→row_to_ticket→repository return→service return→main决定返回工单或项目404→中间件添加响应头→浏览器。

## 关键代码：连接失败并不返回None

源码位置：ticket_app/ticket_repository.py。

```python
with get_connection() as connection:
    cursor = connection.execute(
        "SELECT id, title, status FROM tickets WHERE id = %s",
        (ticket_id,),
    )
    row = cursor.fetchone()

return row_to_ticket(row)
```

先执行get_connection()，它调用psycopg.connect，按settings中的地址/端口/数据库/用户名/密码建立真实连接；当前Compose给api的目标为db:5432。调用成功才把连接交给connection并进入缩进块。

connection.execute把参数化SELECT交给数据库执行；SQL里的%s由驱动用(ticket_id,)参数绑定，单元素元组保留逗号。cursor接住驱动返回的结果对象，fetchone取一行；没有行时才得到None。随后row_to_ticket(None)返回None，逐层回到main.py的ticket变量，由if ticket is None触发404/detail工单不存在。

如果db已停止，psycopg.connect无法正常建立连接，会抛连接异常。此时还未执行SELECT，不会运行后面的fetchone，也不会经正常return把None交给main.py。异常沿repository→service→main.py传出，log_request的except记录异常并重新raise。当前应用没有把数据库连接异常转成友好响应的专用处理，通常由框架返回500/Internal Server Error；以实际HTTP结果为准。这与查询无记录的预期404不同。

此未处理异常还会跳过log_request正常分支中的response.headers设置，所以不要求它必有X-Request-ID；本课观察运行状态与响应差异，不盲找不存在的响应头。网络断开或502也不能直接当作预期数据库500，先恢复db再据结果判断。

## 用户实验：基线、停止、对照、恢复

### 1. 正常基线

浏览器先访问/health，预期200/status:ok。到/docs沿用员工凭据（Authorize填token本身），执行上一课GET /tickets/{ticket_id}，使用上一课已确认不存在的ID；999999999只是此前示例，以实际结果为准。正常基线应为项目404/detail工单不存在。若是401/403等认证失败，先解决认证再停止数据库；认证拒绝无法检验数据库是否可用。

### 2. 上海服务器停止db

如需登录，在Windows PowerShell执行：

```powershell
ssh -o ServerAliveInterval=30 -o ServerAliveCountMax=3 ubuntu@42.192.114.83
```

到Ubuntu提示符后执行以下服务器命令：

```bash
cd /home/ubuntu/ticket-app
sudo docker compose --env-file .env.compose stop db
sudo docker compose --env-file .env.compose ps -a
```

sudo是以相应管理权限执行；docker compose读取项目配置；--env-file沿用既有环境配置文件；stop停止指定服务，db是Compose里的数据库服务名；ps -a显示运行与停止的容器。预期db显示Exited，api仍Up。不要去本机Docker Desktop停另一个db；不关闭Caddy或api。

### 3. 浏览器对照两次真实请求

刷新/health并看Network本次结果，预期仍200。到/docs对同一个ID再次Execute，预期当前代码通常返回500，可能需等待连接失败；不要把上次留在界面的404当成新响应。连接失败时，SELECT尚未成功开始。

如果当前结果不一致，记录实际状态/正文。不要为了得到预期而反复停库或改变密码。

### 4. 立即恢复并核对

在同一个Ubuntu管理窗口执行：

```bash
sudo docker compose --env-file .env.compose start db
sudo docker compose --env-file .env.compose ps -a
```

start启动已有db容器，复用原数据。若仍显示health: starting，几秒后再运行ps -a直到healthy；若没有正常启动，报告实际状态。然后Swagger再次Execute相同请求，正常应恢复原项目404/detail工单不存在。也可在/web/重新加载原有工单，确认原数据仍在。若SSH中途断开，普通SSH重连后cd回项目目录，优先执行start db恢复。

## 读现有Compose时的边界

项目根目录Compose.yaml有depends_on.db.condition: service_healthy，用于Compose按依赖组织启动，等待指定数据库健康检查通过。它不使每一次请求自动验证数据库，也不意味着运行期间数据库永不出故障。现有db健康检查是容器内部的pg_isready，结果不能替代api使用自身配置和权限执行实际工单查询；具体参数语法不在本小段增加教学负担。

restart: unless-stopped也不意味着用户手动stop后自动抵消这次停止，本实验应明确start恢复。不要把health endpoint、Docker健康检查、业务SQL成功三者混成同一个检查。
