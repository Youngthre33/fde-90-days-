## 先看三种职责

| 谁 | 本项目当前职责 | 例子 |
| --- | --- | --- |
| 模型 | 根据收到的标题和状态生成建议文字 | 建议核实恢复情况，确认后结束工单 |
| 工作人员 | 结合实际情况决定是否执行操作 | 核实后点击“完成” |
| 程序 | 按写好的规则形成请求、检查输入/身份、更新数据库 | 从in_progress算出done，PATCH成功后显示已完成 |

模型文字中写“已完成”并不会触发状态按钮或SQL；人工点击也仍需后端正常通过鉴权和输入检查。浏览器代码中的下一状态规则与真正写数据库的代码是不同位置。

## 用现有两个函数定位实际流程

打开ticket_app/web/main.js，用编辑器搜索handleAdviceAction和handleToggleStatusAction。本课以阅读定位为操作，不要求反复请求模型、实际修改工单或新增业务代码。

生成建议的路线：

1. 用户点击生成建议，浏览器进入handleAdviceAction。
2. POST /tickets/20/advice到后端main.py的create_ticket_advice。
3. 后端按编号查询工单，生成ticket_text并请求模型，解析检查后返回结果。
4. 浏览器收到结果，通过adviceOutput.textContent显示三个栏目。

这一段未调用update_ticket_by_id，不包含更新状态的SQL。目前建议也没有新增数据库保存逻辑。无需重讲上一课解析函数内部类型变化。

修改状态的路线：

1. 工单处于in_progress时，render.js显示“完成”按钮；用户点击后进入handleToggleStatusAction。
2. currentTicket取当前浏览器保存的工单，getNextTicketStatus(currentTicket.status)按ticket.js既定规则得到done。
3. 浏览器发送PATCH /tickets/20，请求正文为{"status":"done"}。
4. FastAPI执行既有get_role与TicketUpdate检查，main.py的update_ticket调用ticket_service.update_ticket_by_id，再转ticket_repository.update_ticket_by_id。
5. repository遇到status字段执行UPDATE tickets SET status = %s WHERE id = %s，参数为done和20；查询并返回更新后工单。
6. 浏览器接收updatedTicket，replaceTicket替换对应项，再setTickets与render显示新状态。

当前所有程序步骤都由现有代码安排；模型没有参与getNextTicketStatus的计算。不要把“后端一定要求上一状态是in_progress”当成事实：前端负责算下一状态，后端按现有TicketUpdate规则接受请求，当前此课未新增状态转换限制。

## 代码小段：真正改变状态的位置

ticket_app/ticket_repository.py内update_ticket_by_id现有摘录，仅供阅读：

```python
if "status" in update_data:
    connection.execute(
        "UPDATE tickets SET status = %s WHERE id = %s",
        (update_data["status"], ticket_id),
    )
```

对例子来说，update_data["status"]是done，ticket_id是20。执行的是数据库更新语句，作用于编号20的记录。模型建议中的“关闭”“完成”等文字不会自动运行这里。
