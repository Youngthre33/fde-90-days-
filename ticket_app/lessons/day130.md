# Day130：检查工单修改与删除的关键结果

## 本课解决的问题

Day128 已用一项测试检查创建和重新查询，Day129 让每项测试使用独立的临时 schema。本课继续检查：修改成功后是否真正保存；同一次修改中后一步被数据库拒绝时，前一步是否撤回；删除是否只影响指定工单；接口对首次删除和重复删除各返回什么。

这些测试都在 `ticket_app` 内。测试区域使用 `ticket_app_test`，不是日常工单库。仓储测试直接调用 `ticket_repository`；接口测试中的 `TestClient` 在测试进程内请求 FastAPI 应用，不需要另开网页或 8001 服务。每项测试结束后，Day129 的 fixture 删除本项使用的临时 schema。

## 本课使用的文件

- `tests/test_day130_repository.py`：学习者亲手写的修改成功测试。先创建工单，改状态为 `done`，再重新查询确认已保存。
- `tests/test_ticket_repository.py`：已有的仓储测试；本课逐行学习并单独运行“无效状态导致标题回滚”和“只删除目标工单”两项。此文件其余预写测试不能因为本课两项通过就记为已学。
- `tests/test_ticket_api.py`：已有的接口测试；本课单独运行删除 103 号工单的测试。该测试会预置 101—104 号工单，检查首次 DELETE 为 204、随后 GET 为 404、重复 DELETE 为 404。
- `ticket_repository.py`：真正执行 UPDATE、DELETE 和查询的代码；`schema.sql` 限定状态只能是 `open`、`in_progress` 或 `done`；`main.py` 根据删除结果给请求者返回 204 或 404。

3. 学习者报告 `test_delete_only_target_ticket` 结果符合预期：目标消失，另一张保留，重复删除目标返回 `None`。

## 执行顺序与关键区别

修改失败的顺序：先前的创建已经提交 → 一次 `update_ticket_by_id` 调用先执行标题 UPDATE → 状态 `waiting` 违反数据库规则 → 仓储函数里的连接 `with` 因异常退出，回滚本次未提交的更新 → `pytest.raises` 检查确实出现预期错误 → 重新查询仍看到原工单。`pytest.raises` 不负责回滚；`DROP SCHEMA` 在整项测试结束后清理临时区域，也不是上述回滚的原因。

删除接口的顺序：`TestClient` 发送 `DELETE /tickets/103` → FastAPI 的 `main.py` 调用 service 和 repository → PostgreSQL 删除该编号 → 接口返回空正文的 204。随后 GET 103 查不到而返回 404；再次 DELETE 也返回 404。204 是接口报告处理成功、没有正文；后续查询检查数据库操作后的可见结果。接口这项测试没有单独断言其他预置工单仍在；“只删目标”由前面的仓储测试检查。

## 两道理解题的实际讲评

1. 学习者正确预测失败修改后仍是“原标题、`open`”，但最初把原因误归为 `DROP SCHEMA`。补讲执行顺序后，对迁移情境“去掉 DROP、保留连接 with”回答正确：仍能查到原内容，因为连接 `with` 撤销了本次未提交的修改。临时 schema 此时会残留，属于另一个清理问题。
2. 学习者正确指出若首次 DELETE 返回 204，但随后 GET 103 返回 200，测试会因预期 404 而失败；重新查询用来检查删除后的实际状态。补充澄清：204 的规定含义是处理成功且无正文，不是含义不明；程序仍可能错误地报告成功，所以不能只凭答复断定数据已删除。
