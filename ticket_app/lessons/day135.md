## 第一小段：创建明确的新目标

在包含 `ticket_app_test` 的同一个 PostgreSQL 服务下，对 Databases 右键选择 Create → Database。在 General 中填写：

- Database：`ticket_app_restore_day135`，这是本次接收恢复内容的新库名。
- Owner：`postgres`，使用课程一直使用的本机账号。

在 Definition 中选择 Template 为 `template0`。它是 PostgreSQL 的内置干净模板，用来创建只有标准对象的新数据库，适合作为恢复目标。然后 Save。若提示同名已存在，先报告实际情况，不自动删除或复用已有库。

创建成功后，在新库 `ticket_app_restore_day135` 上右键打开它自己的 Query Tool，执行：

```sql
SELECT current_database() AS db_name;
```

current_database() 取这个查询窗口实际连接的库名，AS db_name 是结果列的显示名称。预期返回 `ticket_app_restore_day135`；左侧选中另一个库不等于旧查询窗口已经更换连接。

## 恢复窗口设置与执行

确认新库连接查询与 Restore 窗口目标均为 `ticket_app_restore_day135` 后，在 General 选择支持 Custom 归档的 `Custom or tar`，Filename 通过文件选择器指向上一课实际生成的备份。Backup 的 Filename 是输出位置，Restore 的 Filename 是输入来源。Number of jobs 设为 1，使用一个恢复任务。

Data Options 的 Pre-data、Data、Post-data 均为 Yes，Only data 与 Only schema 均为 No，恢复结构、数据和索引等。Query Options 中：

- Include CREATE DATABASE statement：No。使用手动创建的目标库；启用该项会按归档里的库名创建并恢复数据库，不适合本次指定新库名的步骤。
- Clean before restore：No。当前目标应为新建库，不先删除已有对象。
- Single transaction：Yes。把本次恢复作为一个事务，全部成功后提交，中途报错则回滚本次事务中的修改；它不撤销此前独立创建新库的操作。

设置后点击 Restore。pgAdmin 调用 `pg_restore` 读取归档，在目标库重建表和相关结构、写入备份中的数据。等待 Processes 中本次 Restore 的状态，核对 Object 指向新库；若 Failed，先读取 More details 的错误，不盲目重跑。成功后下一段再查询实际数据、列与索引。

## 2026-10-01节奏调整与剩余核对安排

学习者说明软件界面与设置操作有基础，这类恢复流程不需要这么多细分课时；密集新代码名称（如conftest）才需要拆分慢讲。此反馈不是新库查询结果，不能据此记数据与结构核对通过。已完成Day134和已有Git历史保留，不重编编号；今后同类备份、恢复和核对通常合成一个Day。

本轮将下面三项与两道关键理解题一次给齐，学习者完成后集中反馈，不再逐按钮等待“继续”。这是给出操作与问题，不是实际通过记录：

1. 从新库节点打开自己的Query Tool，先单独执行 `SELECT current_database() AS db_name;` 核对连接目标，再执行 `SELECT id, title, status, version FROM public.tickets WHERE id = 5;`。与前面的合并查询相比，单独查询库名不会因5号没有行而也失去库名结果。实际库名不符时先更正窗口；没有行或有错误时反馈原始结果。
2. 在新库的Schemas→public→Tables→tickets→Columns→version上右键Properties。Definition的Data Type应为integer；Constraints的Not Null应为Yes、Default Value应为1。仅查看后关闭。默认1是未指定版本的新行起始值，不要求已有5号的当前版本为1。查数据与查列规则是两个检查。
3. 复用Day131已经学过的索引清单查询，核对恢复后的真实索引定义：

```sql
SELECT indexname, indexdef
FROM pg_indexes
WHERE schemaname = 'public'
  AND tablename = 'tickets'
ORDER BY indexname;
```

查询的是当前连接库中public.tickets的索引信息，需按实际输出核对包含tickets_pkey及Day131的day131_tickets_status_id_idx，后者定义应包含(status, id)。不要求只能有两行；网格截断可打开单元格查看完整定义。不要把预期名称写成实际已经恢复的证据。

操作后两道关键理解题：

1. 恢复完成后，只在ticket_app_restore_day135把5号标题改掉。原来的ticket_app_test及日常ticket_app是否随之改变？为什么？
2. 假设新库能查到5号工单，但version的NOT NULL/默认值规则丢失，或Day131索引缺失。能否按本课要求认定结构与数据都核对通过？为什么不能只看能查到一行数据？

学习者第1题答“不会，因为这是一个新的库，只是用之前的备份数据，不会影响之前的库”，判断及理由正确，说明理解恢复新库与原库独立。第2题答“不能，必须要所有的都查到才行”，判断正确；补清“所有”指本课指定的数据、version列规则和索引三项，不要求逐行检查全库。两题通过，不追加重复测验。
