## 业务用途与整体位置

现有AI回答虽然带三个中文栏目，Python仍取得一段字符串。希望把摘要、建议、待补充信息分别放到固定字段，方便程序取值和后续网页分别展示。

目标结构示例（教学示例，不是本次模型实际输出）：

```json
{
  "summary": "用户反馈打印机无法连接，原因待确认。",

  "missing_info": ["打印机型号", "具体报错内容"]
}
```

summary是一段文字；next_steps和missing_info是各装多条文字的数组。JSON是一种数据格式，经过解析后才能作为Python字典和列表按字段使用。当前content仍是字符串，不能把显示了JSON外观视为Python已得到字典。

## 第3段：按规则检查解析结果（待用户操作）

使用Pydantic已安装的BaseModel和Field。main.py中的TicketCreate检查工单输入，这里TicketAdvice检查模型回答的数据结构。与普通函数注解不同，model_validate实际执行检查。

### 文件顶部导入

在ticket_ai.py顶部现有导入处增加：

```python
from pydantic import BaseModel, Field
```

### 在导入之后、generate_ticket_advice之前定义规则

```python
class TicketAdvice(BaseModel):
    summary: str = Field(min_length=1)
    next_steps: list[str] = Field(max_length=3)
    missing_info: list[str] = Field(max_length=3)
```

class TicketAdvice定义数据模型，括号中的BaseModel提供Pydantic检查能力，此处不是调用生成函数，也不是DeepSeek大模型。summary的str要求字符串，min_length=1要求至少1个字符；list[str]是列表且元素为字符串，max_length=3限制列表项目数，并非每条建议字数。没有提供字段默认值，三个字段必需；空列表符合至多3条的要求。长度规则以Pydantic当前文档为准，本段不引入额外regex或strict配置。

### 替换文件末尾的parser

```python
def parse_ticket_advice(content: str) -> dict:
    data = json.loads(content)
    advice = TicketAdvice.model_validate(data)
    return advice.model_dump()
```

json.loads先得到普通Python数据。本次JSON对象得到字典data。TicketAdvice.model_validate(data)按模型规则校验，成功生成TicketAdvice对象由advice接住；不合规则抛ValidationError，不会继续下一行。advice.model_dump()把已通过本次检查的模型对象转换为普通字典，再return给调用者，维持终端使用advice['summary']的方式；该方法不会保存文件或写数据库。链条是模型文字→字典→按规则检查/创建对象→字典→调用者。

这里原来的data字典和返回字典类型相同，增加的价值在中间的实际规则校验，不是必须改变最终数据类型。模型对象是本机Python中的数据对象，不是AI在再次工作。
