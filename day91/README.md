# Day 91：通过网页修改工单标题和处理状态

## 今天完成什么

接着 Day 90 的创建、删除，完成标题保存、状态切换和失败后重试，让客户能通过网页更新后端工单。
本节使用 Day91 的六个前端文件，继续复用 Day90 后端，没有新增 Day91 Python 服务。
学习重点是：请求成功后才更新浏览器数据；取消不保存；失败时保留输入，允许修改后重试。

## 谁在做什么

| 角色 | 真实工作 |
| --- | --- |
| 5500 网页文件服务 | 将 HTML、JavaScript 文件交给浏览器 |
| 浏览器中的 JavaScript | 读取输入，直接向 8001 发请求，收到回复后更新网页 |
| 8001 Python 后端 | 检查请求，更新内存工单，返回结果 |
| 两个终端 | 启动服务、查看日志，供开发者操作 |

工单请求不会先交给 5500 转发。`127.0.0.1` 表示访问者自己的电脑，当前两个服务都在本机。

## 文件分工

| 文件 | 职责 |
| --- | --- |
| `index.html` | 页面结构，`action-message` 显示保存和状态更新提示 |
| `constants.js` | 状态、动作名称及 `http://127.0.0.1:8001/tickets` 地址 |
| `data.js` | 保存浏览器当前的 `tickets`；`setTickets` 替换这份数组 |
| `ticket.js` | 计算下一状态，按编号用后端返回的完整工单替换旧工单 |
| `render.js` | 根据数组和 `editingId` 重建列表；编辑中的工单禁用状态按钮 |
| `main.js` | 接收点击、发送请求，协调数据、页面和操作提示 |

实际保存使用 `replaceTicket`；`ticket.js` 保留的 `editTicket` 没有用于这条保存流程。
后端入口为 `day90/main.py`，更新函数在 `day90/ticket_service.py`，启动入口为 `day90.run`。

## 启动与访问

在仓库根目录打开后端终端；如果旧后端占用 8001，先停止旧进程，再执行：

```powershell
.\.venv\Scripts\python.exe -m day90.run
```

当前 `day86/.env` 将端口配置为 8001，以启动日志为准。另一个终端提供网页文件：

```powershell
.\.venv\Scripts\python.exe -m http.server 5500 --bind 127.0.0.1
```

已有 5500 服务可继续使用。打开 [Day91 页面](http://127.0.0.1:5500/day91/index.html)。
网页来源仍是 `http://127.0.0.1:5500`，继续使用 Day90 的 CORS 配置。

## 先分清三份内容

| 内容 | 在哪里 | 什么时候改变 |
| --- | --- | --- |
| 编辑草稿 | 网页输入框的 `value` | 用户打字时改变，尚未保存 |
| 浏览器工单数据 | `data.js` 的 `tickets` 数组 | GET 加载成功，或写请求成功后调用 `setTickets` |
| 后端工单数据 | Python 进程内存中的 `tickets` | 后端执行创建、修改、删除时改变 |

输入框打字不会自动修改另外两份数据。浏览器和后端通过 JSON 传递内容，不共享同一个数组对象。
`editingId` 只记录哪条工单正在编辑；`render` 清空列表并根据浏览器数组重新创建输入框和按钮。
因此，重新渲染编辑行会用数组里的标题重新填写输入框，未保存的草稿可能被覆盖。

## 保存标题：PATCH 流程

```text
点击“编辑” → editingId = 工单编号 → render 显示输入框
修改输入框，点击“保存”
  → handleSaveAction 禁用当前保存按钮，显示“正在保存工单标题...”
  → 读取 editInput.value，发送 PATCH /tickets/编号
  → 请求正文只带 title，例如 {"title":"客户无法登录"}
  → TicketUpdate 检查输入，路由提取本次提供且不是 None 的字段
  → update_ticket_by_id 找到工单，ticket.update(update_data) 更新标题
  → 后端回复 200 和完整工单，包括 id、title、status
  → 浏览器检查 response.ok，再用 response.json() 读取结果
  → replaceTicket 按编号替换旧工单，setTickets 保存新数组
  → editingId = null，render 退出编辑，显示“工单标题已更新”
  → finally 执行按钮恢复代码
```

没有发送 `status` 就不会覆盖原状态；后端找不到编号时返回 404，不会执行浏览器里的成功更新步骤。
点击“重新加载工单”会再次 GET `/tickets`，用后端回复替换浏览器数组；标题仍在，说明后端当前内存已经保存它。

## 切换状态：PATCH 流程

```text
点击状态按钮 → handleToggleStatusAction 禁用当前按钮，显示更新中提示
  → 从浏览器 tickets 找到工单，getNextTicketStatus 计算下一状态
  → PATCH /tickets/编号，请求正文只带 status
  → 后端校验状态并更新内存工单，回复 200 和完整工单
  → replaceTicket → setTickets → render → 显示“工单状态已更新”
  → finally 执行按钮恢复代码
```

| 当前状态 | 按钮 | 下一状态 |
| --- | --- | --- |
| `open`（待处理） | 开始处理 | `in_progress`（处理中） |
| `in_progress`（处理中） | 完成 | `done`（已完成） |
| `done`（已完成） | 重新打开 | `open`（待处理） |

下一状态由浏览器计算，后端检查它是否属于三个允许值；本次只发送状态，不会覆盖标题。

## 取消、失败与重试

- **取消：**将 `editingId` 设为 `null` 并 `render(tickets, editingId)`，恢复数组里的标题；不发送 PATCH，不修改后端。
- **空标题失败：**`title: ""` 不符合 `min_length=1`，后端返回 422；`response.ok` 为假，代码主动抛错进入 `catch`。
- **保留输入：**保存的 `catch` 只显示失败提示并记录 Console 错误，没有 `setTickets`、清除 `editingId` 或 `render`，因此输入框及当前草稿保留。
- **继续重试：**`finally` 在成功或失败后都会执行；失败时恢复原保存按钮，可在原输入框补写标题，再点保存。
- **状态失败：**显示“更新失败,请稍后重试”，不替换浏览器数组、不重新渲染，并在 `finally` 恢复状态按钮。

保存成功后的 `render` 已重建列表按钮；`finally` 操作的是原按钮引用。失败时没有重建，恢复的就是页面上原来的按钮。
保留草稿依赖于没有其他操作重建列表；重新加载、切换编辑对象等操作仍可能覆盖尚未保存的输入。

下面是整组核对的预期结果，可配合 F12 → Network／网络查看请求；无需每次学习都反复跑一遍。

## 当前边界与下一步

- 后端改动只在内存中，不会自动写回 `day82/ticket_store.py`；重启后端恢复初始数据，刷新网页与重启后端是两件事。
- 当前不会自动去掉空格；空字符串会失败，只含空格的标题仍能通过，后续再完善校验。
- 请求期间只禁用本次点击的按钮；编辑行另行禁用状态按钮。没有锁住整页，其他操作或重新渲染仍可能与请求交错。
- 失败提示目前较概括；创建和删除失败仍主要记录在 Console，本节新增的页面提示用于标题保存和状态更新。
